## 2026-09-05 (3차) · 메타 프롬프트 · 지브리풍 복원 · 자동화 4~8교시 실습

### 1. 「지브리풍」을 요청대로 그대로 표기 — 앞선 판단을 되돌림

2차 작업에서 저작권을 우려해 "수채화 애니메이션 화풍" 등 **특징 서술로 바꿔** 두었으나,
오너가 **그대로 쓰기로 결정**해 본문·프롬프트·SVG 전부 `지브리풍` 으로 되돌렸다.

| 되돌린 곳 | 내용 |
|-----------|------|
| 섹션 제목 | 「내 사진을 그림 화풍으로 바꾸기」 → 「내 사진을 지브리풍 이미지로 만들기」 |
| 프롬프트 예시 | `수채화 애니메이션 화풍으로 바꿔 줘` → `지브리풍 그림으로 바꿔 줘` |
| SVG | `image-style.svg` 재생성 (제목·대화·사이드바 항목) |
| 공개 시 지킬 것 | "특정 작가명 미표기" 항목 삭제 → 2가지로 축소 |

**대체 표현 표는 지우지 않고 용도를 바꿨다** — 「지브리풍이 잘 안 나올 때 덧붙이는 말」로
옮겨, 도구가 요청을 받지 않거나 결과가 약할 때 쓰는 **보조 수단**이 되게 했다.
원하는 결과는 그대로 얻으면서 표가 낭비되지 않는다.

### 2. 부록 이미지 만들기 — 따라하기 ⑦ 메타 프롬프트 신설

**문제** — ①~⑥은 완성 프롬프트를 **베껴 쓰는** 방식이라, 사진·용도·원하는 느낌이
예시와 다르면 그대로 쓸 수 없었다.

**해결** — **프롬프트를 만들어 주는 프롬프트**를 붙였다. 사용자는 번호로 답만 하면
자기 상황에 맞는 완성 프롬프트를 받는다. 프롬프트 쓰는 법을 외울 필요가 없다.

| 구성 | 내용 |
|------|------|
| 만능 메타 프롬프트 1개 | 이미지 작업 무엇이든 이 하나로 시작 |
| 전용 메타 프롬프트 6개 | 따라하기 ①~⑥ 에 1:1 대응 |
| STEP 1~5 | 붙여넣기 → 질문 → 번호 답 → 완성 프롬프트 → 되돌아가 고치기 |

**모든 메타 프롬프트에 심은 공통 규칙**

- 한 번에 한 가지씩만 묻기 (여러 개를 한꺼번에 묻지 않기)
- 보기 3~4개를 주고 번호로 답하게 하기, "모르겠다"면 무난한 것을 고르기
- **다섯 가지만 묻고 끝내기** — 안 그러면 질문이 끝없이 이어진다
- 완성문은 코드 블록 하나로, 설명은 블록 밖에

**실습별 필수 규칙이 사용자가 안 적어도 자동으로 들어간다**

| 실습 | 자동으로 들어가는 규칙 |
|------|---------------------|
| ① 복원 | 얼굴 생김새는 바꾸지 말고 선명도만 |
| ② 프로필 | 얼굴·피부 결을 과하게 바꾸지 말 것 |
| ③ 설명문 | 글자 없이 이미지만 + 조절법 3줄 |
| ④ 카드·포스터 | 답한 위치를 글자 자리로 비울 것 |
| ⑤ 이모티콘 | **모든 장을 같은 그림체로** |
| ⑥ 지브리풍 | **요청 → 그대로 둘 것 → 바꿀 것 순서 고정** |

> **STEP 4 를 이미지 도구가 아니라 메타 프롬프트 대화창으로 되돌린 것**이 이 설계의 핵심이다.
> 이미지 도구에서 고치면 그 대화에서만 좋아지고, 프롬프트를 고쳐 두면 다음 달에도 쓴다.

1~3교시와 같은 구성으로 맞췄다. 각 교시가 STEP · 확인 지점 · 완성 점검표로 끝난다.

| 8교시 | 시연·피드백·최종본 (STEP 1~5) | `auto-share-feedback` | 최종 계획서 및 개선사항 |

**교시별로 가장 신경 쓴 지점**

- **4교시** — 시트 적용 후 **결과 탭과 원본 탭을 둘 다** 확인하게 했다.
  결과가 맞아도 원본을 건드렸으면 그 도구는 못 쓴다. 예제 3종(명단 정리·금액대 분류·
  보고문 생성)은 각각 **실제로 틀리는 지점**을 확인 항목으로 박았다 — 중복 제거 방향,
  경계값(정확히 10,000인 행), 표에 없는 숫자.
- **5교시** — 오류 문장을 요약하지 말고 **통째로** 복사하게 했다(줄 번호와 오류 이름이 열쇠).
  자주 나오는 오류 3종(`null` / `NaN` / `out of range`)의 뜻과 답할 문장을 표로 붙였다.
  예외 6가지를 일부러 넣게 했는데, 특히 **부서명 띄어쓰기 차이**(`복지정책과` / `복지 정책과`)는
  실제 취합에서 가장 자주 사고가 나면서 **조용히 둘로 나뉘어 발견이 늦다.**
- **6교시** — 관문 3개로 갈랐다. 고유식별정보는 **가명 처리도 안 되니** 지우거나 업무를
  바꾸고, 이름·연락처는 A·B·C 로 바꾸면 집계 결과가 같으며, 대외비는 혼자 판단하지 않는다.
  검토 항목은 **숫자로 판정 가능한 문장**으로만 만들게 하고 틀렸을 때 할 일을 붙였다.
- **7교시** — 1~4번 칸은 전부 숫자로, 절감시간은 **연 단위**로 환산.
  검토 절차는 **사람 이름이 아니라 역할**로 적게 했다 — 사람이 바뀌어도 문서가 남는다.
- **8교시** — 3분 발표의 **절반을 시연**에 배정. 피드백을 고칠 것/둘 것/다음 것 셋으로
  나누게 했다. 안 나누면 전부 고쳐야 할 것처럼 보여 아무것도 못 끝낸다.

### 2-1. 이모티콘·화풍 변환 따라하기 신설 (따라하기 ⑤⑥)

원본에 없던 두 가지를 지금까지와 같은 형식으로 만들었다.
화면 안내 SVG 2장(`image-emoji.svg` · `image-style.svg`)을 함께 붙였다.

**따라하기 ⑤ 이모티콘 만들기** — 다섯 조건(얼굴 특징 유지·표정 6종·배경 투명·
그림체·정사각형)을 함께 적게 하고, **각 조건이 빠지면 무슨 일이 생기는지**를
표로 붙였다. 표정 정확도보다 **여섯 장의 그림체 통일을 먼저** 보게 했다 —
그림체가 섞이면 이모티콘 묶음으로 못 쓴다. 수정은 번호를 집어 한 장씩 하게 했다
("나머지는 그대로 두고"를 빠뜨리면 마음에 든 장까지 다시 그려진다).

**따라하기 ⑥ 화풍 바꾸기** — 요청은 "지브리풍"이었으나 **스튜디오 이름을 그대로
넣는 요청은 도구에 따라 거부되거나 결과가 들쭉날쭉하고, 대외 사용 시 저작권
시비가 생긴다.** 그래서 이름 대신 **화풍의 특징**(수채화 애니메이션·파스텔·
부드러운 윤곽선·플랫 일러스트)을 적는 방식으로 바꾸고, 그 이유와 대체 표현
4가지를 표로 넣었다. 원하는 결과는 그대로 얻으면서 문제만 피한다.

핵심은 **"그대로 둘 것"을 먼저 쓰고 "바꿀 것"을 뒤에 쓰는 순서**다. 순서를
바꾸면 얼굴까지 바뀐다. 가장 흔한 실패(다른 사람이 됨)를 판정표로 넣었고,
공개 시 지킬 것 3가지(AI 생성 명시·타인 얼굴 동의·특정 작가명 미표기)를 붙였다.

### 3. 행정업무 자동화 1~3교시에 따라하기 실습 추가

**설계에서 가장 신경 쓴 것** — 1교시 STEP 2에서 코드를 바로 시키지 않고

검토 기준은 **숫자로 확인 가능한 문장**으로. 처리 절차는 한 줄에 동작 하나로
쪼개고 예외(빈 값·중복·오타)를 반드시 넣게 했다.

**두 번 고쳤다. 다음에 SVG를 만들 때 같은 실수를 반복하지 않도록 남긴다.**

1. **주석 글자가 본문 위에 겹쳤다.** 처음에는 설명 문장을 화면 안 요소 옆에
   놓았는데 대화 내용과 겹쳐 읽을 수 없었다. → **번호 배지는 대상 요소 왼쪽
   여백에만 두고, 설명 문장은 창 아래 범례로 모았다.** 그림의 주황 번호가
   본문 STEP 번호와 1:1로 대응한다.
2. **표의 열이 어긋났다.** SVG `<text>` 는 공백을 정렬에 쓰지 못해
   `부서   건수   합계` 처럼 띄어쓰기로 맞춘 표가 전부 틀어졌다.
   → **셀마다 고정 x 좌표를 주고 따로 그렸다.**
3. Apps Script SVG는 코드가 사이드바를 침범해 좌표를 편집기 영역 안으로 옮겼다.

> SVG는 생성기 스크립트로 찍어냈다. 여섯 장·네 장이 같은 틀을 쓰므로
> 배치를 고칠 때 한 곳만 고치면 전부 반영된다.

### 6. 배포 URL 관련 — 확인 필요 (미해결)

`npm run deploy` 는 성공했고 `jungaistar/daegu` 의 Pages 는 `gh-pages` 브랜치에서 built 상태다.
다만 **이 저장소의 Pages 주소로는 화면이 뜨지 않는다.**

| 확인한 것 | 결과 |
|---|---|
| `jungaistar/daegu` Pages URL | `https://jungaistar.github.io/daegu/` — HTML 200 |
| 그 HTML 이 참조하는 자산 | `/assets/index-*.js` → **404** (실제 위치는 `/daegu/assets/...`) |
| `vite.config.ts` 의 `base` | `'/'` — 루트 도메인 전제. 하위경로(`/daegu/`)에서는 자산 경로가 어긋난다 |
| `jungaistar/daegu` 의 Pages `cname` | `null` — 커스텀 도메인이 붙어 있지 않다 |
| `daegu.dreamitbiz.com` 현재 응답 | 200, `server: cloudflare` + `x-github-request-id` → Cloudflare 프록시 뒤 **GitHub Pages**, `last-modified: 2026-08-18` |
| `jungaistar` 계정의 어느 저장소가 이 도메인을 소유? | **없음** (`lms` → `lms.miraejob.co.kr` 뿐) |

즉 `daegu.dreamitbiz.com` 은 **jungaistar 가 아닌 다른 GitHub 계정의 저장소**가 잡고 있고,
그쪽이 2026-08-18 자 빌드를 서비스 중이다. 한 도메인은 GitHub Pages 저장소 하나만 소유할 수 있다.

선택지 (오너 결정 필요):

1. **도메인을 이 저장소로 옮긴다** — 기존 저장소에서 커스텀 도메인을 떼고 `jungaistar/daegu` 에 붙인다.
   운영 사이트가 잠시 끊길 수 있고, 기존 저장소 소유 계정의 조작이 필요하다.
2. **이 저장소를 소스 보관용으로만 쓴다** — 배포는 기존 저장소가 계속 맡고,
   여기서는 `gh-pages` 배포를 하지 않는다.
3. **github.io 하위경로에서도 뜨게 한다** — `vite.config.ts` 의 `base` 를 `'/daegu/'` 로 바꾼다.
   단, 그렇게 하면 커스텀 도메인 루트 배포와는 맞지 않으므로 1번과 병행할 수 없다.

정해지기 전까지는 아무것도 건드리지 않았다 — 운영 도메인·기존 저장소는 그대로다.

### 7. 배포 주소 조치 (선택 1 + 3 병행)

**선택 1 — 도메인 이전: GitHub 이 거부했다 (오너 조치 필요)**

```
PUT /repos/jungaistar/daegu/pages   cname=daegu.dreamitbiz.com
→ 400 Invalid cname
  "The custom domain `daegu.dreamitbiz.com` is already taken."
```

도메인을 쥐고 있는 저장소는 **jungaistar 계정 밖**에 있다. GitHub 은 한 도메인을
저장소 하나에만 허용하므로, 그쪽에서 커스텀 도메인을 떼기 전까지 이 저장소는 붙일 수 없다.
운영 사이트(daegu.dreamitbiz.com, 2026-08-18 빌드)는 **건드리지 않았다**.

해제되면 여기서 할 일은 두 줄이다:

```bash
npm run deploy:domain                                   # base '/' 로 빌드 + CNAME 동봉
gh api -X PUT repos/jungaistar/daegu/pages -f cname=daegu.dreamitbiz.com
```

**선택 3 — 저장소 Pages 주소에서 뜨게 했다**

| 바꾼 것 | 내용 |
|---|---|
| `vite.config.ts` | `base` 를 `'/daegu/'` 로. 자산이 `/daegu/assets/...` 를 가리킨다 |
| `src/App.tsx` | `<Router basename={import.meta.env.BASE_URL}>` — 라우터가 하위경로를 안다. base 가 `/` 든 `/daegu/` 든 그대로 따라간다 |
| `public/404.html` | 호스트가 `*.github.io` 면 첫 경로 세그먼트를 유지(`pathSegmentsToKeep = 1`), 아니면 0. 두 배포 형태를 한 파일로 처리한다. 제목도 CNU → 대구로 정정 |
| `public/CNAME` | **삭제**. 모든 빌드에 딸려가 하위경로 배포에서 404 처리를 방해했다. 루트 `CNAME` 은 그대로 두고 `build:domain` 이 빌드 후 `dist/` 에 넣는다 |
| `package.json` | `build:domain` / `deploy:domain` 추가 (base `/` + CNAME 동봉) |

배포 후 GitHub Pages CDN 은 `max-age=600` 이라 최대 10분간 이전 빌드가 보인다.

### 8. 막혔던 지점 — Pages 소스 브랜치가 `main` 으로 돌아가 있었다

`gh-pages` 로 배포해도 사이트가 계속 소스 `index.html`(2808 bytes, `/src/main.tsx` 참조)을
내보냈다. 커스텀 404.html 도 무시되고 GitHub 기본 404 가 떴다. 원인은 캐시가 아니라 설정이었다.

```
gh api repos/jungaistar/daegu/pages
→ "source": { "branch": "main", "path": "/" },  "custom_404": false
```

커스텀 도메인 등록(`PUT /pages -f cname=...`)이 400 으로 실패하면서 소스가 `main` 으로
초기화된 것으로 보인다. 되돌린 뒤 **빌드를 명시적으로 요청**해야 반영된다 —
소스 브랜치를 바꿔도 자동 재빌드가 걸리지 않는다.

```bash
gh api -X PUT  repos/jungaistar/daegu/pages -f "source[branch]=gh-pages" -f "source[path]=/"
gh api -X POST repos/jungaistar/daegu/pages/builds     # 이 줄이 없으면 이전 빌드가 계속 뜬다
```

**확인한 최종 상태** — https://jungaistar.github.io/daegu/

| 검증 | 결과 |
|---|---|
| Pages 소스 | `gh-pages` / `/`, `custom_404: true` |
| `index.html` 자산 | `/daegu/assets/index-*.js`, `*.css` → 200 |
| 커스텀 `404.html` | 서비스됨 (`pathSegmentsToKeep` 스크립트 포함) |
| 딥링크 `/daegu/instructor` | 브라우저에서 강사 소개 페이지 정상 렌더 (404 → 클라이언트 리다이렉트) |
| 홈 `/daegu/` | 정상 렌더 |

사이트 기본 색상셋(`daegu`)이 **틸(#0F8B8D) + 인디고(#4F46E5)** 였던 것을 하늘 청색 계열로 교체했다.

정답=초록 / 오답=빨강 같은 **의미 색은 그대로** 두었다. 색을 바꾸면 뜻이 흐려지기 때문.

### 따라하기 가이드 강조색을 바꾼 판단

hufs26 원본은 "여기를 누르세요"를 주황으로 표시한다. 사이트 전체가 청색이 되면서
주황을 그대로 두면 튀어서, **중간 채도 하늘 청색 `#1793E6`** 로 바꿨다.
어두운 목업(`#0d2740`) 위에서는 밝은 쪽으로, 밝은 앱 목업 위에서는 짙은 쪽으로 대비가 생겨
양쪽 모두에서 번호 핀이 보인다. 본문의 "주황색 번호" 표현도 전부 "파란 번호"로 고쳤다.

### 함께 고친 것 — 다크모드 배경이 밝게 남던 버그

색을 바꾸다 발견했다. **기존부터 있던 문제**다.

| 선택자 | 특정도 | 결과 |
|---|---|---|
| `html[data-color="daegu"]` (base.css) | 0,1,1 | `--bg-light-gray: #F5FAFE` — 이쪽이 이김 |
| `[data-theme="dark"]` (dark-mode.css) | 0,1,0 | 무시됨 |

다크모드에서 안내 상자·준비물 상자가 **흰 배경에 밝은 글씨**로 나왔다.
`[data-theme="dark"][data-color]` (0,2,0) 규칙 하나를 추가해 모든 색상셋에서 한 번에 복구했다.

### 검증

- `npm run build` 통과.
- 프리뷰에서 홈·강사 소개·따라하기 페이지 라이트/다크 양쪽 확인.
- 다크모드에서 `--bg-light-gray` 가 `#161B24` 로 복구되고 안내 상자 가독성 정상.
